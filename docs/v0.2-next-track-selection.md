# v0.2 Next Track Selection

状态：`accepted recommendation`

## 1. Purpose

本文用于在 v0.1 developer demo、Track D Demo / Docs Polish、Track A HTTP API Minimal Surface 都收口后，选择 v0.2 下一条最合适的 implementation track。

本轮目标不是实现新功能，而是避免惯性进入 real HTTP server、memory storage、external ingestion 或 real LLM。下一 track 应提升 v0.2 demo 的可用性，同时继续保持 kernel hard contracts：canonical event log 是 source of truth，artifact / memory / checkpoint 不成为第二事实源，所有 side effect 仍受 policy / grants 约束。

## 4. Recommendation

推荐下一阶段选择：

**Track C: Artifact content read policy / controlled full-content retrieval**

理由：

- 它最直接提升 v0.2 demo 可用性：当前 demo 能展示 artifact summary/ref/provenance，但不能展示“如何在授权下读取具体 artifact content”。
- 它能继续强化 Isotope 的核心边界：default summary-only、ref-first access、explicit grants、no implicit full-content read。
- 它复用当前已存在的 `ArtifactStore`、`RetrievalService`、`ResourceRef`、HTTP facade deferred full-content route 和 no-content-read tests。
- 它不需要 real HTTP server、network listener、FastAPI / Flask、新依赖、real LLM、memory storage 或 external provider。
- 它可以为后续 External Ingestion / ImportedSnapshot 打基础：外部 raw input 最终也需要 artifact capture、summary view 和 controlled full-content access。

建议范围应保持很窄：

- 第一批 boundary docs、red tests 和 green slice 已完成。
- read policy / grants shape 已有 slice-only implementation。
- 默认仍只返回 summary / ref / provenance。
- full-content read 必须显式授权，且 response shape 不能混入 projected `RunState`。
- HTTP full artifact content route 当前继续 deferred；当前已有 enablement guard，只有后续 red tests 明确要求 controlled endpoint 时才可打开，而且必须是 in-process facade endpoint，不是真实 network server。

## 5. Why Not Real HTTP Server

不要优先做 real HTTP adapter / network wrapper。

原因：

- Track A 已经证明 server-facing API shape，继续加 network listener 对 kernel contract 的新增价值有限。
- real server 会引入 process lifecycle、ports、request parsing、timeouts、logging、安全默认值和 framework 选择问题。
- FastAPI / Flask / ASGI / WSGI 一旦引入，容易把 framework behavior 写进 kernel docs 和 tests。
- 对外观而言，network server 容易让 v0.2 被误读为 hosted / product API 已可用。
- 当前目标仍是 developer demo / runtime slice，不是 hosted service。

real server boundary 只有在 Track A 被显式 reopened 时再设计。

## 6. Second Choice

第二选择是：

**Track E: Minimal approval pause/resume boundary**

它有可见价值，因为 pending approval 已经存在；但 resume 会牵涉：

- approval resolve event shape。
- pending run 如何恢复 action execution。
- idempotency 与 duplicate resume。
- denied / approved / stale approval 的 lifecycle。
- server / HTTP facade 是否暴露 approval endpoint。

因此它比 Track C 更容易碰到 projector lifecycle 和 executor re-entry 语义。建议在 Track C 后再进入，或者先单独做 approval resolve boundary docs。

## 7. Deferred / Not Next

以下不作为下一默认 track：

- real listening HTTP server / network wrapper。
- FastAPI / Flask / new dependencies。
- real memory query engine or memory storage。
- external ingestion implementation。
- SSE / streaming。
- full approval API product flow。
- plugin system。
- real LLM integration。
