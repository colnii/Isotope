# Unified Read Approval Design

Date: 2026-06-11

## Goal

Make file reading understandable from Desktop chat by exposing one user-facing
read action while preserving separate execution boundaries for workspace code
and local files outside the workspace.

The immediate user case is a chat request such as:

```text
read \\wsl.localhost\Ubuntu\tmp\resume62\6.2.md
```

The model should not say it lacks all read ability. It should understand that
workspace reads are already available, while local-file reads need explicit
operator approval.

## Product Contract

Expose one product concept:

```text
read
```

The action has an explicit `scope`:

- `workspace`: read a workspace-relative file from the current `cwd`.
- `local_file`: read one absolute or platform-local file path outside the
  workspace after approval.

Examples:

```json
{
  "scope": "workspace",
  "path": "src/isotope/capabilities/code_access.py"
}
```

```json
{
  "scope": "local_file",
  "path": "\\\\wsl.localhost\\Ubuntu\\tmp\\resume62\\6.2.md"
}
```

## Current Context

`code.read` already implements a real workspace read. It intentionally accepts
only workspace-relative paths and rejects absolute paths, parent traversal, and
Windows drive paths. That boundary is correct for code inspection.

Desktop already has a pending-approval surface in
`ConversationWorkspace.svelte`, `appState.resolveApproval(...)`, the desktop
agent client, and the `/desktop/approvals/{id}/resolve` backend endpoint. This
should be reused. The missing piece is a read-specific approval request shape
and user-facing detail text for local-file reads.

## Architecture

Keep the existing runner separation internally:

1. `read(scope="workspace")` routes to the existing `code.read` runner.
2. `read(scope="local_file")` creates an approval-gated runtime action.
3. The Desktop approval card shows the target path, scope, and read-only nature
   of the request.
4. When approved, the local-file runner reads a bounded text excerpt and returns
   public metadata plus a stable file reference.
5. When denied, the conversation loop receives a structured denial observation
   and answers with the boundary rather than hanging.

The model sees a single read capability in the capability manifest. The system
keeps implementation-specific runner choices behind the capability boundary.

## Safety Model

Workspace read:

- allowed by default;
- path must stay inside `cwd`;
- returns bounded text excerpts and metadata;
- no approval required.

Local-file read:

- approval required for the first slice;
- one approval authorizes one read request, not a directory or session grant;
- path must resolve to a regular file;
- binary and unsupported encodings return metadata-only status;
- text content is excerpt-limited;
- no write, delete, execute, or directory traversal behavior is bundled.

Persistent directory grants are out of scope for the first slice. They can be
added later if one-off approval becomes too noisy.

## Desktop UX

Reuse the current pending approval panel instead of creating a new permission
system.

For local-file reads, the approval card should show:

- title: `读取本地文件`;
- source: runtime approval;
- detail: the normalized path and excerpt limit;
- actions: `拒绝` and `批准`.

The card should not imply broad or permanent filesystem access. The default
approval reason can remain generated by the frontend, but the requested action
summary must be specific enough that the operator knows exactly which file will
be read.

## Conversation Behavior

When the user asks to read a workspace-relative file, the model should call
`read` with `scope="workspace"` and answer from the returned observation.

When the user asks to read an absolute, UNC, or otherwise external path, the
model should call `read` with `scope="local_file"`. If approval is needed, the
UI shows the pending request. The model should not report a capability gap just
because the path is outside the workspace.

If the user denies the request, the answer should say the file was not read
because local-file access was denied.

## Data Shape

The unified read result should use one top-level result key, even if the
underlying runner differs:

```json
{
  "status": "completed",
  "read": {
    "scope": "workspace",
    "status": "readable",
    "path": "src/app.py",
    "excerpt": "...",
    "truncated": false,
    "byte_count": 123,
    "line_count": 7,
    "ref": {
      "ref_type": "code",
      "scope": "workspace",
      "path": "src/app.py",
      "sha256": "..."
    }
  }
}
```

For local files, the `ref.scope` is `local_file` and the path is displayed only
as the approved path. Later slices may redact home-directory prefixes, but the
first slice should preserve enough path detail for user confirmation.

## In Scope

- Add a user-facing `read` capability contract.
- Reuse `code.read` for workspace scope.
- Add a local-file read runner behind approval.
- Reuse the existing Desktop approval resolution endpoint and pending approval
  card.
- Add read-specific approval summary projection.
- Update conversation observations so final answers can cite read results.
- Add targeted unit and desktop integration tests.

## Out Of Scope

- Permanent directory grants.
- Session-wide filesystem permissions.
- Recursive directory reads.
- Raw binary file projection.
- Writing, deleting, executing, or editing local files.
- Replacing `code.search`; search remains workspace-scoped for now.

## Testing

Targeted verification should prove:

- Workspace-scope `read` returns the same bounded excerpt behavior as current
  `code.read`.
- External paths no longer become a capability gap when local-file read is
  available.
- Local-file `read` creates a pending approval before reading.
- Denied local-file approval returns a controlled denial observation.
- Approved local-file read returns bounded text excerpt plus metadata.
- The Desktop approval card displays a read-specific path summary and can
  resolve through the existing `/desktop/approvals/{id}/resolve` endpoint.
