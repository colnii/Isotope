## 版本 1：普通 AI App 结构

类似：

```text
src/
├── agents/
├── tools/
├── memory/
├── rag/
├── prompts/
├── api/
└── utils/
```

这个版本适合：

```text
聊天机器人
RAG 问答
单 agent + tools
轻量 demo
课程项目
短期 MVP
```

它的问题是：**现在写得快，但未来会混。**

因为你的目标不是普通 AI app，而是：

```text
能操作电脑
能接外部应用
能衍生子功能
能分化 agent
能长期记忆
能自我改造
能写代码
能扩展能力
```

这种情况下，`tools/`、`agents/`、`memory/` 很快不够用了。

比如：

```text
tools/
├── shell.py
├── browser.py
├── gmail.py
├── vscode.py
├── computer.py
├── mcp.py
└── generate_new_tool.py
```

这时候 `tools/` 已经混了：

```text
原子工具
外部应用连接器
电脑控制
MCP adapter
技能生成器
执行环境
权限边界
```

所以普通结构的问题不是“错”，而是**它承载不了你的后期野心**。

## 版本 2：AI-OS-ready MVP 结构

我后来给你的精简版大概是：

```text
src/aios/
├── contracts/
├── kernel/
├── agents/
├── capabilities/
├── memory/
├── runtime/
├── policy/
├── llm/

```

这个版本的思想是：

> 先保留未来 AI OS 的关键边界，但不要一上来铺满所有系统。

它适合你**现在这个阶段**。

因为你目前代码都是 Python，项目还早期，没必要马上创建：

```text
desktop/
daemon/
observability/
evolution/
orchestration/
context/
sandboxes/
connectors/
workflows/
```

这些目录。

但是你应该提前保留几个最关键的边界：

```text
contracts/      核心协议
kernel/         主循环
agents/         agent 定义
capabilities/   能力注册
memory/         记忆系统
runtime/        执行环境
policy/         权限安全
llm/            模型网关
```

这个版本的优点是：

```text
不会太重
但未来不会堵死
```

也就是我说的：

> **目录像未来，代码像现在。**

## 三个版本的核心区别

| 版本              | 核心定位           | 适合阶段        | 优点          | 缺点       |
| --------------- | -------------- | ----------- | ----------- | -------- |
| 普通 AI App       | 快速做一个 agent 应用 | demo / 短期项目 | 写得快         | 后期重构痛    |
| AI-OS-ready MVP | 小型内核，预留未来边界    | 你现在最适合      | 不重，但不堵未来    | 需要一点架构自律 |
| 完整 AI OS        | 目标态平台结构        | 中后期 / 长期项目  | 边界最清晰，可扩展性强 | 早期可能显得空  |

## 你喜欢的版本为什么更清晰？

因为它把“运行代码”和“配置系统”分开了。

比如：

```text
packages/agents/
```

是 agent 系统的实现代码。

而：

```text
agents/
```

是用户级、项目级 agent 配置。

也就是说：

```text
packages/agents/      怎么运行 agent
agents/               有哪些 agent
```

这个区分很重要。

同理：

```text
packages/capabilities/   能力系统的实现
skills/                  具体技能包
connectors/              具体外部应用连接配置
```

也就是：

```text
capabilities/   能力平台
skills/         可插拔能力包
connectors/     外部应用实例
```

这就已经不是普通项目了，而是平台化项目。

---

## `apps/` 和 `packages/` 的区别

```text
apps/
```

是用户入口。

比如：

```text
desktop/     桌面端
web/         Web 控制台
cli/         命令行
api/         HTTP/WebSocket
daemon/      后台常驻服务
```

这些都只是“壳”。

真正的系统能力不应该写死在 `apps/` 里。

比如 CLI 里不要直接写：

```python
run_agent()
call_openai()
write_memory()
run_shell()
```

而应该只是调用：

```text
packages/kernel/
packages/agents/
packages/capabilities/
packages/memory/
```

也就是说：

```text
apps/ 是入口
packages/ 是内核
```

以后你从 CLI 扩展到 Web、Desktop、Daemon，不需要重写核心逻辑。

---

## `kernel/` 和 `orchestration/` 的区别

这两个最容易混。

```text
kernel/
```

负责“单次任务如何跑起来”。

比如：

```text
收到用户请求
创建 session
构造上下文
调用 agent
处理 tool call
写回 memory
返回结果
```

而：

```text
orchestration/
```

负责“多个 agent / 多步骤任务如何被组织”。

比如：

```text
规划任务
拆分子任务
分派给 coder / researcher / operator
等待多个 agent 返回
合并结果
失败重试
任务图调度
```

简单说：

```text
kernel = 操作系统内核
orchestration = 调度器 / 工作流引擎
```

早期你可以不单独建 `orchestration/`，先放在 `kernel/` 里。
等多 agent 任务真的复杂了，再拆出去。

---

## `capabilities/` 和 `runtime/` 的区别

这也是关键。

```text
capabilities/
```

回答的是：

> AI 能做什么？

例如：

```text
读文件
写文件
搜索网页
调用 Gmail
控制浏览器
运行 Python
修改代码
生成 PPT
接 MCP server
```

而：

```text
runtime/
```

回答的是：

> 这些能力在哪里、以什么权限、用什么隔离方式运行？

例如：

```text
本机 shell
Docker sandbox
浏览器 profile
远程 worker
虚拟机
受限 workspace
```

所以：

```text
shell.run
```

是一个 capability。

但它可以运行在：

```text
host runtime
docker runtime
restricted runtime
remote runtime
```

这里的区分非常重要。MCP 的架构也是类似思想：Host 通过 Client 连接不同 Server，每个 Server 暴露工具、资源和能力，这本质上就是把“能力提供方”和“宿主应用”分开。([模型上下文协议][1])

---

## `memory/` 和 `context/` 的区别

很多 AI 项目会把这两个混在一起。

```text
memory/
```

是长期存在的东西：

```text
用户偏好
项目知识
历史任务
agent 经验
共享黑板
长期事实
```

而：

```text
context/
```

是这一次模型调用时临时塞进 prompt 的东西：

```text
这轮任务需要哪些记忆？
哪些文件要放进上下文？
token budget 怎么分？
旧消息怎么压缩？
哪些规则优先级更高？
```

简单说：

```text
memory = 仓库
context = 本次取货和打包
```

Claude Code 专门把 subagents 用来做任务隔离和上下文管理，这说明“多 agent 系统里如何控制上下文污染”本身就是一层工程问题，不应该只靠随手拼 prompt。([Claude][2])

---

## `policy/` 和 `runtime/` 的区别

```text
runtime/
```

是执行。

```text
policy/
```

是能不能执行、执行前要不要审批、执行后怎么审计。

比如：

```text
删除文件
发邮件
提交 git commit
运行 rm -rf
安装依赖
读取浏览器 cookie
修改系统设置
```

这些不是简单工具调用，而是权限问题。

Claude Code 的 hooks 文档里就有很多和生命周期事件相关的设计，比如在某些工具运行前后触发逻辑；这类机制本质上就是为了让权限、安全、审计可以插入 agent 运行流程。([Claude][3])

所以你这个项目从第一天就应该有 `policy/`，哪怕最开始只有很薄的一层。

---

## `evolution/` 是完整版本里最“未来”的目录

```text
evolution/
```

负责：

```text
分析自身项目结构
提出新能力设计
生成新 skill
生成新 connector
修改代码
写迁移计划
跑测试
回滚
生成 changelog
```

这个目录不应该早期就写满。

但是你喜欢的完整结构里把它单独列出来是对的，因为它代表你的核心愿景：

> AI 不只是使用系统，而是能改造系统。

只是要注意：
`evolution/` 不能绕过 `policy/` 和 `runtime/`。

正确链条应该是：

```text
evolution 提案
→ policy 风险判断
→ runtime 隔离执行
→ tests/evals 验证
→ 人类审批
→ 合并
```

这就像 Strangler Fig pattern 的思想：不要一次性推倒重写，而是通过稳定边界和渐进替换降低重构风险。Martin Fowler 对这个模式的解释就是用逐步替换来减少 cut-over rewrite 的风险。([martinfowler.com][4])

---

## `observability/` 为什么也要单独有？

因为 AI 系统最可怕的问题是：

```text
它为什么这么做？
哪一步调用了哪个工具？
哪条记忆影响了这次输出？
哪个 agent 改了哪个文件？
失败发生在哪一轮？
能不能回放？
```

普通 Web 后端只要 log request/response。

但 agent 系统要记录：

```text
user message
agent decision
tool call
tool result
memory read
memory write
policy decision
context pack
model output
runtime action
```

所以 `observability/` 不是传统日志目录，而是：

```text
tracing
event replay
debug timeline
agent decision audit
```

早期可以不建，或者只放一个 `events.log`。
但完整 AI OS 结构里应该有它。

---

## 顶层 `skills/`、`agents/`、`workflows/` 为什么不放进 `packages/`？

因为它们更像“用户资产 / 项目资产”，不是核心代码。

```text
packages/skills_runtime/     技能系统怎么运行
skills/                      具体有哪些技能
```

```text
packages/agents/             agent 框架怎么实现
agents/                      具体定义了哪些 agent
```

```text
packages/orchestration/      工作流引擎怎么跑
workflows/                   具体有哪些工作流
```

这个分离会让你的系统以后很像：

```text
引擎 + 插件 + 配置 + 工作区
```

而不是所有东西揉在源码里。

这也和现在 agent 生态的方向一致：比如 Agent Skills 这种做法，就是把一个能力打包成独立目录，用说明文档和附带脚本/资源表达能力；而不是把所有能力都写死进主程序。([Claude][2])

## Python 项目里怎么落地这版？

因为你现在是 Python，我建议把核心代码放进 `src/`：

```text
my-ai-os/
├── apps/
├── src/
│   └── aios/
│       ├── kernel/
│       ├── orchestration/
│       ├── agents/
│       ├── memory/
│       ├── capabilities/
│       ├── runtime/
│       ├── llm/
│       ├── context/
│       ├── policy/
│       ├── evolution/
│       ├── observability/
│       └── contracts/
├── skills/
├── agents/
├── workflows/
├── connectors/
├── memory_store/
├── workspaces/
├── sandboxes/
├── evals/
├── docs/
├── scripts/
├── tests/
├── pyproject.toml
└── README.md
```

也就是说，把你喜欢的：

```text
packages/
```

在 Python 里映射成：

```text
src/aios/
```

这样更符合 Python packaging 的习惯。PyPA 文档对 `src` layout 的解释是：它把真正可导入的代码放在 `src/` 下，避免项目根目录里的工具文件、配置文件被意外 import。([Python 打包用户指南][5])

所以最终不是：

```text
packages/kernel/
```

而是：

```text
src/aios/kernel/
```

概念不变，只是 Python 落地方式更自然。
