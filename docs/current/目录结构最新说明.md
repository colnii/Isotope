你这个质疑是对的。
我上一版里 `assistant/` 和 `features/*_assistant/` 确实不规范，主要问题是**概念层级混乱**：

```text
assistant/
features/project_assistant/
features/file_assistant/
features/research_assistant/
```

这会让人分不清：

```text
assistant 到底是产品本体？
还是一个 agent？
还是一个 feature？
还是一个 service？
```

而且 `features/` 下面再放一堆 `*_assistant`，等于每个 feature 都在重复产品名，语义很脏。

---

## 先定原则：assistant 不应该到处出现

我建议：

> **Isotope 整体可以被称为 assistant，但代码目录里不要到处叫 assistant。**

就像一个 Web 项目整体叫 app，但你不会到处写：

```text
user_app/
file_app/
chat_app/
search_app/
```

代码目录应该表达职责，而不是产品宣传语。

OpenAI Agents SDK 里对 agent 的定义是“能计划、调用工具、协作、保持状态完成多步任务的应用”，这说明 `agent` 是一个具体运行实体，不应该和泛泛的 `assistant` 混用。([OpenAI开发者][1])
而 handoff 机制里，不同 agent 负责不同专门任务，这也更支持用 `agents/coder.py`、`agents/researcher.py` 这种角色名，而不是到处叫 `assistant`。([OpenAI][2])

## 我会把 `assistant/` 改名

原来：

```text
src/isotope/
├── assistant/
│   ├── session.py
│   ├── message_loop.py
│   ├── task_loop.py
│   └── response.py
```

我现在更建议改成：

```text
src/isotope/
├── runtime/
│   ├── session.py
│   ├── conversation_loop.py
│   ├── task_loop.py
│   ├── dispatch.py
│   └── response.py
```

或者更产品化一点：

```text
src/isotope/
├── core/
│   ├── session.py
│   ├── conversation.py
│   ├── task.py
│   ├── dispatch.py
│   └── response.py
```

我更推荐 **`core/`**，因为它不夸张，不像 `kernel/` 那么 OS 化，也比 `assistant/` 清楚。

## `features/` 下面也不该叫 `*_assistant`

原来：

```text
features/
├── chat/
├── task_runner/
├── project_assistant/
├── file_assistant/
├── research_assistant/
└── capability_builder/
```

建议改成：

```text
features/
├── chat/
├── tasks/
├── projects/
├── files/
├── research/
├── automation/
└── capability_building/
```

这里的区别是：

| 原名                   | 问题                       | 新名                    |
| -------------------- | ------------------------ | --------------------- |
| `project_assistant`  | 重复 assistant，像角色不是功能     | `projects`            |
| `file_assistant`     | 像一个人，不像模块                | `files`               |
| `research_assistant` | 和 `agents/researcher` 混淆 | `research`            |
| `task_runner`        | 可以，但偏实现细节                | `tasks`               |
| `capability_builder` | 可以，但名词化更统一               | `capability_building` |

## 每一层现在的含义

### `core/`

负责 Isotope 的主流程。

```text
用户输入
→ session
→ conversation
→ dispatch
→ feature / agent / capability
→ response
```

它不是“内核”，也不是“某个助手”，而是产品运行核心。

---

### `features/`

负责真实用户功能。

```text
chat         对话功能
tasks        任务管理、任务拆解、任务执行
projects     读项目、理解项目、修改项目
files        文件读写、整理、转换
research     检索、总结、引用
automation   自动化流程
capability_building  从需求生成新能力
```

这里应该是**面向用户场景**的，不是面向 agent 角色的。

---

### `agents/`

负责智能角色。

```text
chief        主控 agent
planner      规划 agent
coder        写代码 agent
researcher   研究 agent
operator     操作电脑/工具 agent
evaluator    检查结果 agent
```

这里才应该出现“人味儿”的角色名。

---

### `capabilities/`

负责可调用能力。

```text
tools        原子工具
skills       组合技能
registry     能力注册表
schemas      能力描述结构
```

---

### `execution/`

负责执行环境。

```text
shell
python
sandbox
browser
approvals
```

---

### `workspace/`

负责项目文件、git、快照、回滚。

---

## 为什么这样更规范？

因为它把三种东西分开了：

```text
feature      用户想做什么
agent        谁来做
capability   具体怎么做
```

比如用户说：

> 帮我重构这个项目结构。

系统里应该是：

```text
features/projects
  → 调用 agents/planner
  → 调用 agents/coder
  → 调用 capabilities/tools/filesystem
  → 调用 execution/shell
  → 写入 memory
```

而不是：

```text
project_assistant
  → 里面什么都有
```

后者很快会变成巨型模块。

---

## 如果你想更像 Python 项目，还可以这样命名

Python 项目里比较自然的是：

```text
services/
domain/
adapters/
```

但你这个项目是 AI 应用，我不建议太传统后端化。
保留 `features/ agents/ capabilities/` 是合理的。

另外，继续用 `src/` layout 是对的。Python Packaging Authority 对 `src` layout 的解释是：它能把项目根目录里的配置、工具文件和真正可导入的包隔开，避免开发时 import 到错误位置的代码。([Python 打包用户指南][3])

## 我现在会给 Isotope 定一个更准确的目录语义

```text
apps/          入口
core/          产品主流程
features/      用户场景
agents/        智能角色
capabilities/  可调用能力
memory/        持久上下文
workspace/     工作区与项目文件
execution/     执行环境
integrations/  外部系统接入
policy/        权限与安全
platform/      底层机制，暂时不要扩大
common/        通用工具
```

这样比之前干净很多。

所以你的直觉是对的：

> `assistant/` 这个目录名最好删掉。
> `features/*_assistant` 也最好删掉。
> Isotope 作为产品可以是 assistant，但代码结构里应该用更精确的工程名。
