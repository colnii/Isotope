# v0.2 Mid-Cycle Review

状态：`accepted recommendation`

## 1. Purpose

本文用于在 v0.2 中段复盘当前已经 closed 的 tracks，并选择下一条默认 implementation track。

本轮不是实现新能力，也不是发布 release。目标是避免惯性进入 real HTTP server、memory query engine、external ingestion implementation 或 real LLM，同时继续让 v0.2 demo 更像可验证的 runtime slice。

## 2. Current Baseline

当前已完成：

- `v0.1-demo` tag 已存在，developer demo accepted。
- Track D: Demo / Docs Polish 已 `effectively complete / closed for now`。
- Track A: HTTP API Minimal Surface 已 `effectively complete / closed for now`。
- Track C: Artifact Content Read Policy 已 `effectively complete / closed for now`。
- 当前 baseline：`682 passed`。
- HTTP API 仍是 in-process `HttpApiApp` / `create_http_app(...)`，不是 real network server。
- memory 仍是 boundary-only，不是 durable storage / query product。
- checkpoint v0.1 仍 frozen。
- real LLM、real HTTP server、external ingestion、approval resume、semantic retrieval / ranking 都仍 deferred。

## 3. What v0.2 Has Proved So Far

v0.2 已经把 v0.1 developer demo 推进到更可交互、更可验证的 runtime boundary：

- demo/docs 能让新读者理解并运行 deterministic kernel loop。
- in-process HTTP facade 暴露了 session / run / input / state / events / artifact summary surface。
- request validation、response contract、idempotency、route inventory 和 deferred route contract 已由 tests 锁住。
- artifact summary 与 controlled full-content retrieval boundary 已明确：summary 默认不返回 full content，full-content retrieval 只在 retrieval layer，且必须使用 structured `ResourceRef`、grants、caller context 和 purpose。
- HTTP full-content route 仍 `501 not_enabled`，避免把 retrieval boundary 误读成 public content API。

## 5. Recommendation

推荐下一阶段选择：

**Track E: Minimal approval pause/resume boundary**

理由：

- approval 已有基础：`approval.requested` event、pending projection 和 no-execution / no-artifact boundary 已存在。
- 它能直接验证 kernel hard contracts：pending run 不能被 executor 隐式推进，resume 必须受 canonical events、policy decision 和 lifecycle rules 约束。
- 它有 v0.2 demo 可见价值：用户能看到 action chain 被 policy / approval gate 暂停，而不是只有成功路径。
- 它可以继续保持 in-process、no network、no real LLM、no new dependency。
- 相比 External Ingestion，它不需要先定义 provider quality / freshness / coverage semantics。
- 相比 real HTTP server，它更能验证 kernel contract，而不是引入 transport/runtime lifecycle 问题。

## 6. Why Not The Other Tracks Now

不要优先做 Track B real HTTP adapter / network wrapper：

- Track A 已证明 server-facing API shape。
- real server 会引入 ports、process lifecycle、timeouts、framework choice、logging/security defaults 和 hosted product expectation。
- 这些问题对 kernel contract 的新增验证价值低。

不要优先做 Track G memory query engine：

- memory v0.1 已 frozen to boundary / read-model / checkpoint。
- 即使 tiny query slice，也容易被读成 real memory product capability。
- query engine 会快速牵出 ranking、exposure、promotion、controlled expand 和 storage policy。

不要优先做 Track F external ingestion implementation：

- ingestion 很重要，但比 approval 更容易牵涉 provider-specific assumptions。
- `ImportedSnapshot` 需要先写清 raw artifact capture、quality / freshness / source metadata 和 projection boundaries。
- 建议 Track F 先做 docs / red tests，不要直接进入 implementation。

Track H 可以继续做，但不应阻塞 v0.2 core boundary work。

## 7. Suggested Next TDD Entry Point

下一轮建议先做 docs-only boundary：

```text
docs/approval-pause-resume-boundary-v0.2.md
```

随后 red phase 可以新增：

```text
tests/isotope_kernel/test_approval_resume_boundary.py
tests/isotope_kernel/test_http_api_approval_deferred_boundary.py
```

第一批 red tests 应覆盖：

- pending approval 已存在时不能自动执行。
- approving 必须绑定 existing `approval.requested` / decision / proposal。
- denied approval 不能执行 action，也不能创建 artifact。
- stale / duplicate approval resolve 必须 fail closed。
- resume 后 action lifecycle 必须保持 canonical order。
- resume 不允许绕过 `PolicyDecision.grants`。
- HTTP approval route 当前仍 deferred，除非该 slice 明确进入 in-process approval endpoint。
- no real HTTP server / no new dependencies。
